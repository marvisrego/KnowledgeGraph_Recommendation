📊 Part 1: Data Processing Steps (One-Time Setup)

ℹ️ Important: These steps happen ONCE during setup. The resulting graph and embeddings are stored on disk and reused for every user query. No rebuilding needed unless source data changes.
1 Load Source Data
Input Files:
  • ONET_Data.xlsx (US occupational database) → 1,016 roles + 4,000 skills/elements
  • ESCO CSV Files (European skills framework) → 3,039 roles + 14,000 skills
2 Parse ONET Data
What happens: src/onet_preprocessing.py reads Excel
  • Extract 1,016 role nodes (e.g., "Data Scientist", "Manager")
  • Extract ~4,000 element nodes (knowledge, skills, abilities)
  • Create ~120,000 REQUIRES edges (role → element) with importance levels (0–5)
  • Filter: only keep ONET importance ≥ 3.0 (exclude low-priority skills)
3 Parse ESCO Data
What happens: src/esco_preprocessing.py reads CSV files
  • Extract 3,039 role nodes (e.g., "Data Analyst", "Software Engineer")
  • Extract ~14,000 skill nodes (ESCO skill taxonomy)
  • Create ~115,000 REQUIRES edges (role → skill) marked 'essential' or 'optional'
  • Build hierarchies: BROADER_THAN, NARROWER_THAN, ISCO group membership
4 Merge into Single Graph
What happens: src/graph_build.py
  • Combine ONET + ESCO nodes & edges into one NetworkX DiGraph
  • No collisions: prefix nodes with "ONET_" or "ESCO_" to distinguish sources
  • Result: 22,259 total nodes | 235,501 total edges (mostly REQUIRES)
5 Create Cross-Dataset Alignment
What happens: graph_build.py with embeddings
  • For each of the 1,016 ONET roles: embed it (call API)
  • For each of the 3,039 ESCO roles: embed it (call API)
  • ~41 API batches total to embed all 4,055 roles
  • Compare embeddings: calculate cosine similarity between every ONET ↔ ESCO pair
  • If similarity ≥ 0.45: create SIMILAR_TO edge (bidirectional)
  • Result: 25,262 SIMILAR_TO edges bridging the two datasets
6 Save Graph to Disk
What happens: Serialize the complete graph
  • Write to: graph/graph.gpickle (~500 MB, binary format)
  • Load time: 2–3 seconds at server startup
  • Benefit: Graph now in memory for millisecond-fast queries
7 Pre-Compute & Index Embeddings
What happens: src/embeddings_index.py`
  • Take the 4,055 role nodes (from Step 5)
  • For each role: extract text (title + description + essential skills)
  • Call Azure embedder for each role → get 3072-dimensional vector
  • Store all 4,055 embeddings in ChromaDB (vector database)
  • Save to disk: index/chroma/
  • Benefit: At runtime, user query → embed in 1 API call → search 4,055 roles in milliseconds

🧠 Part 2: All AI Models & What They Do

⚡ Key Point: All models run on Azure Cognitive Services. Each has a specific job in the pipeline.
🤖 Model 1: text-embedding-3-large
Type Embedding Model
Vector Size 3,072 dimensions
Purpose Convert text → numbers for comparison
When Called During build (41 times) + Runtime (1 per query)

What it does: Takes text (role title + description) and converts it into a 3072-dimensional vector. Similar roles get similar vectors (cosine distance). Used to:

  • During setup: Embed all 4,055 roles to find cross-dataset matches (SIMILAR_TO edges)
  • At runtime: Embed user's query to find relevant roles in ChromaDB

🏆 Model 2: Cohere Rerank v4.0-pro
Type Ranking/Reranking Model
Input Query + 50 candidates
Output Top-5 scored candidates
When Called Every user query (Step 3 of pipeline)

What it does: Takes query + 50 candidate roles, re-scores them for relevance, returns top-5. Why needed? Embedding search is fast but sometimes imprecise. Cohere reads the query & candidate text more deeply and fixes ranking mistakes.

💬 Model 3: gpt-5.4-nano (Reasoning Model)
Type LLM (Reasoning)
Used For Routing + Generation
Token Budgets Routing: 2k | Gen: 4k
Special Feature Internal chain-of-thought

What it does: This is the "thinking" model. It has two jobs:

  • Job 1 (Step 1 - Routing): Analyzes conversation history. Detects: Is user a student or professional? Do they have enough info (degree/role, skills, goal)? Returns: JSON with user type + context flag
  • Job 2 (Step 5 - Generation): Reads full history + graph data + user query. Generates conversational career advice (3–4 paragraphs, no bullets). Only mentions roles/skills from the graph.
Why "reasoning"? It uses internal chain-of-thought before outputting. This improves quality but uses extra tokens, so budgets are set high (2k/4k).

Model Usage Summary

Model Job Called When Why This Model?
text-embedding-3-large Text → 3072D vector Setup (41×) + Runtime (1×) Fast semantic search; finds similar roles
Cohere Rerank Score 50 → top 5 Every query (Step 3) Deep relevance scoring; fixes embedding mistakes
gpt-5.4-nano Routing + Generation Every query (Steps 1 & 5) Reasoning + conversation; understands intent & context

Step-by-Step: How KG Uses Embeddings

A Extract Text from Roles
For each of 4,055 roles (ONET + ESCO):
  • Combine: role title + description + essential skills (as text)
  • Example: "Data Scientist — analyze data using statistics, machine learning, Python, SQL"
B Call Embedding API for Each Role
For each role text:
  • Send to Azure text-embedding-3-large
  • Receive back: 3,072-dimensional vector (array of 3,072 numbers)
  • Batch API calls: Send multiple roles per call (41 total batches)
  • Each vector captures the semantic meaning of that role
C Compare Vectors: Find Similar Roles
Now we have 4,055 vectors (one per role):
  • Compare every ONET role vector to every ESCO role vector
  • Use cosine similarity (measures angle between vectors: 0 to 1)
  • If similarity ≥ 0.45: create SIMILAR_TO edge
  • Example: ONET "Data Analyst" (0.78 similar) ↔ ESCO "Data Analyst"
D Result: 25,262 SIMILAR_TO Edges
  • Each SIMILAR_TO edge stores the cosine similarity score
  • Users navigating ONET careers can now find equivalent ESCO careers
  • Creates a bridge between US & European job markets

Where Are Embeddings Stored?

graph_build.py (creates embeddings) ↓ embeddings_index.py (stores in vector database) ↓ ChromaDB (persistent vector store) ↓ Directory: index/chroma/ ├─ vectors.db (4,055 embedding vectors) ├─ metadata/ (role IDs, titles, sources) └─ Ready for fast cosine search at runtime

Embedding Benefits

✓ Pre-computed: All 4,055 role embeddings calculated once, stored in ChromaDB. No rebuild unless roles change.
✓ Fast retrieval: User query → embed (1 API call) → search 4,055 roles → top 50 in ~100ms
✓ Semantic matching: Finds related roles even if keywords don't match (e.g., "data work" matches "Data Analyst")

🔄 The 6-Step Pipeline: User query flows through 6 steps, each calling specific models/services. Happens every time a user sends a message.

Input: Full conversation history (all messages so far)

What it does:

  • Detects user type: student vs professional?

  • If context complete: return {"has_context": true, "user_type": "student"}
Why this step? Routing early saves API calls if we need more info from user

Key Insight:
  • 3 model API calls per query: 2× gpt-5.4-nano + 1× embedding + 1× rerank
  • 1 in-memory graph traversal (milliseconds, no API call)
  • 1 HTTP scrape (Coursera, variable time)
  • Total round-trip: ~3–4 seconds
  • All previous queries' data (graph + embeddings) cached on disk/RAM

💬 Part 5: Example Prompts - Complete vs Incomplete

ℹ️ How Step 1 (ROUTE INTENT) Works: The LLM reads the conversation and checks:
  • For STUDENT: Has degree/field? Has skills? Has career goal? → All 3 needed
  • For PROFESSIONAL: Has current role? Has experience/skills? Has next step goal? → All 3 needed
